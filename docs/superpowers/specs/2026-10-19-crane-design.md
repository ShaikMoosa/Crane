# Crane MVP design

## Intent

Build an original local desktop notes application that captures the best interaction ideas of Bear: a focused Markdown editor, flexible inline tags, quick search, and a quiet three-pane information architecture. The app should feel immediately usable on Windows while keeping the Rust + Tauri v2 + vanilla JavaScript architecture reusable across desktop platforms.

## Goals

- Make creating, finding, and editing a note feel instant.
- Keep all note data local and available offline.
- Derive organization from inline `#tags` and lightweight note states.
- Provide a polished desktop interface with strong keyboard support.
- Preserve data safely across restarts and failed writes.

## Non-goals for the MVP

- Bear branding or pixel-perfect reproduction.
- Cloud sync, accounts, collaboration, encryption, OCR, attachments, drawing, PDF/DOCX export, nested tag icons, or mobile applications.
- Full CommonMark rendering or WYSIWYG editing.

## User experience

The primary view has three regions:

1. A narrow charcoal library rail with Notes, Pinned, Archive, Trash, and discovered tags.
2. A warm-paper note list with search, create action, title, excerpt, modification time, and tag chips.
3. A spacious editor with title, metadata, plain Markdown body, formatting shortcuts, preview toggle, save state, and quiet note actions.

The wide layout shows all three. Medium windows collapse the library rail. Compact windows show one region at a time with a back path. Creating a note selects it and focuses the title. Selecting another note flushes the pending save first. Search and tag filters combine. Trash is recoverable; permanent deletion is intentionally absent from this MVP.

## Data model

Each note contains:

- `id`: stable string generated by the Rust backend;
- `title`: user title;
- `body`: Markdown source;
- `tags`: derived unique normalized tags;
- `created_at` and `updated_at`: Unix milliseconds;
- `pinned`, `archived`, and `trashed`: state flags.

The store contains `schema_version` and `notes`. Rust serializes it to the app data directory as `notes.json` through a temporary sibling and rename. State-changing commands persist before returning success.

## Native command surface

- `bootstrap() -> StorePayload`
- `create_note() -> Note`
- `save_note(request) -> Note`
- `set_note_state(request) -> Note`

No command accepts a filesystem path. The frontend performs display filtering but Rust remains authoritative for persisted note state and tag extraction.

## Failure behavior

- Failed loads retain an empty in-memory store and return an actionable startup error.
- Failed saves leave the editor content in place, show a persistent error, and allow retry.
- Invalid IDs and oversized title/body values are rejected by Rust.
- Moving a note to trash never deletes its content.

## Visual direction

The product uses the metaphor of a manuscript edited with a red pencil: warm mineral paper, graphite navigation, restrained ember-red annotations, soft blue-gray metadata, and a serif editorial voice paired with a highly legible UI sans. The signature interaction is an ember save pulse that travels through the editor status once a native write lands. It is subtle, disabled under reduced motion, and never hides content.

## Accessibility

Use semantic landmarks and buttons, visible focus, 4.5:1 body contrast, screen-reader status announcements, large enough targets, and a reduced-motion path. Editor and preview are real text surfaces; controls have labels independent of icon shape.

## Assumptions made for this build

- The requested "clone" means feature and interaction inspiration, not copied implementation or branding.
- A polished local MVP is preferable to shallow parity with Bear's cloud, OCR, encryption, attachment, and export features.
- Windows is the first development target; the architecture remains cross-platform.
